# 手の並べ替えとSEE

[alpha-beta法とPVS](alphabeta.md)で見たとおり、最初の1手で最善手（または `beta` を超える反駁手）を引ければ、残りの何十手という候補は読まずに打ち切れます。逆に言えば、全合法手を生成して重い判定をすべて前計算してから1手目を読むのでは、すぐ beta cutoff するノードで大きな無駄が出てしまいます。

そこで `src/search/ordering.rs`・`history.rs`・`see.rs` では、**有力な手から段階的に生成・取り出しを行い、高価な計算をギリギリまで遅らせる**設計を採っています。

---

## 1. 「静かな手」の定義と不成の省略

並べ替えや後述の枝刈り・LMR では、各手を「戦術的な手」と「静かな手（`quiet`）」に分けて扱います。`ordering.rs` の `is_quiet` は次のように定義されています。

- **戦術的な手（`quiet = false`）**：駒を取る手すべて、および駒を取らない**歩・香・飛の成り**（と金・成香・龍は駒の働きが劇的に変わるため）
- **静かな手（`quiet = true`）**：駒を取らない通常の移動・駒打ち、および駒を取らない**銀・桂・角の成り**（特に銀や桂の不成・成りは敵陣で手数を稼ぐだけの変化が多く、静かな手と同様に履歴で並べ替えて枝刈り・縮小の対象にします）

また、主探索のルート以外のノード（`ply > 0`）では、実戦上ほとんど最善にならない**歩・角・飛の不成（成れる移動での不成）**を候補生成の段階で除外し、無駄な分岐を減らしています。

---

## 2. `MovePicker` による段階的な手の取り出し

王手がかかっていない主探索ノードでは、最初から全合法手を生成せず、`MovePicker` が次の5つのステージを順番に進めます（毎ノードのヒープ確保を避けるため、`ply` ごとに用意した `OrderingBuffer` を再利用します）。

```text
[1. TtMove] ──► [2. 勝ち・互角の捕獲] ──► [3. キラー手] ──► [4. 静かな手] ──► [5. 損な捕獲 (Deferred)]
```

1. **`TtMove`（置換表の最善手：スコア `1,000,000`）**
   置換表に記録されていた `best_move` が現局面で合法であれば、他の手を1手も生成する前にまずこの1手だけを返します。ここで beta cutoff すれば、手の生成コストは実質ゼロです。
2. **`Captures`（駒取りと歩・香・飛の成り）**
   `rsshogi` の `Captures` 生成器で戦術的な手だけを生成し、「取る駒の価値・成りボーナス・王手ボーナス（`+4,175`）」で仮ソートします。そして**実際に1手ずつ取り出す瞬間に SEE（静的交換評価）を計算**し、`SEE >= 0` ならそのまま返し、`SEE < 0`（取り合いで損をする手）なら後回し用の `deferred` バッファへ退避します。
3. **`Killers`（キラー手：第1候補 `80,000` / 第2候補 `70,000`）**
   同じ探索深さ `ply` の兄弟局面で直近に beta cutoff を起こした「静かな手」を最大2手まで記憶しておき、静かな手の一括生成を行う前に合法性を確かめて試します。
4. **`Quiets`（静かな手と上位16手の部分ソート）**
   ここで初めて `Quiets` 生成器で残りの静かな手を生成し、後述するメイン履歴＋継続履歴で点数付けします。80手近くある静かな手をすべて完全ソートするのは無駄が多いため、`select_nth_unstable` を使って**上位16手だけを先に整列（`sort_quiet_prefix`）**し、17手目以降は本当にそこまで探索が進んだときにだけ次の16手を整列します。
5. **`Deferred`（後回しにした損な捕獲）**
   ステージ2で `SEE < 0` と判定された駒取りを、静かな手のあとに最後に取り出します。

なお、王手回避中（`in_check`）や静止探索（`qsearch`）のように最初から候補手リストが渡される場面では、`Stage::All` モードで捕獲層と静かな手の二層に分けて遅延整列します。また、疑似合法手生成器から得た手は `is_legal_generated` で自殺手（ピンされた駒の移動など）と打ち歩詰めだけを軽量に弾いてから探索へ渡します。

## 3. 履歴ヒューリスティクス（`src/search/history.rs`）

駒損得のない「静かな手」同士の優劣をつけるため、探索中に beta cutoff を起こした手を学習して点数化する2種類の履歴テーブルをワーカーごとに持っています。

### 脅威マス別メイン履歴（Threat-indexed Main History）

通常のメイン履歴は `[手番][移動元または打つ駒種][移動先マス]` の表ですが、このエンジンではさらに**相手の利き（`threatened_squares` ビットボード）**を遅延計算し、次の4レーンに分割しています。

- 移動元が相手の利きに晒されているか（`from_threat`：駒を逃がす手か）
- 移動先が相手の利きに晒されているか（`to_threat`：利きの中へ踏み込む手か）

これにより「当たりになっている銀を逃げる手」と「何もないところへ銀を活用する手」が混ざらずに学習されます。

静かな手で beta cutoff が起きたときは、残り深さに比例するボーナス `min(169 * depth - 53, 1675)` をその手へ加え、逆に**その手より前に試して cutoff しなかった静かな手（最大32手、`TriedQuiets`）にはボーナスの `105%` にあたるペナルティ（malus）**を引きます。値の更新には、絶対値が大きくなるほど増減が緩やかになり自然に `±16,384` 以内へ収束する **gravity 式（`entry += delta - entry * |delta| / 16384`）** を使っています。

### 継続履歴（Continuation History）

「相手が `△３四歩` と突いた直後には `▲２六歩` が良い」といった**直前の手順とのつながり**を学習するのが継続履歴です。

1手前（相手の応手）と2手前（自分の前の手）の `[移動後の駒 × 81マス]` を文脈キーとし、さらに**直前の手が駒取りだったかどうか**でテーブルを分けています（駒取りの直後と静かな駒組みの最中では好手の傾向がまったく異なるためです）。並べ替え時にはメイン履歴に対して継続履歴の合計を `229 / 256` 倍（`continuation_weight = 229`）して足し合わせます。

## 4. 静的交換評価 SEE（`src/search/see.rs`）

**SEE（Static Exchange Evaluation）** は、探索木を広げずに**「ある1つのマス目の上で、お互いに最も安い駒から順番に取り合ったとき、最終的に何点の損得になるか」**をビットボード上で高速に試算する仕組みです。

### 取り合い計算のイメージ

たとえば、相手の金（550点）が守っている相手の銀（450点）を、自分の歩（100点）で取る手と、自分の飛車（1000点）で取る手を比べてみます。

- **歩で銀を取る場合**：まず自分が銀（`+450`）を得ます。相手が金でその歩を取り返しても失うのは歩（`-100`）だけなので、差し引き **`+350` 点の得（`SEE >= 0`）** となり、優先して読むべき捕獲と判定されます。
- **飛車で銀を取る場合**：自分が銀（`+450`）を得た直後、相手が金で飛車（`-1000`）を取り返せるため、差し引き **`-550` 点の損（`SEE < 0`）** となり、`MovePicker` では `Deferred` ステージへ後回しにされます。

途中のどの段階でも「これ以上取り返すと損をする側」はそこで手を止める（stand pat する）権利があるため、配列を後ろから畳み込むミニマックス計算で最終損得が決まります。

### 高速化と王手・ピンへの配慮

- **閾値つきの早期終了（`static_exchange_ge` / `quiet_static_exchange_ge`）**
  ProbCut や SEE 枝刈りでは「正確な点数がいくつか」ではなく「損得が閾値 `threshold` 以上かどうか」だけ分かれば十分です。最初の1〜2回の取り合いで勝敗が確定した瞬間に残りの利き列挙を打ち切ることで計算量を削っています。
- **X線（影の利き）とピン・玉の扱い**
  盤上の駒が取り除かれると、その背後にいた香・角・飛（馬・龍）の利きが新たに通るため、スライディング駒の影の利きを順次追加しながら交換を進めます。また、初期局面で自玉にピンされている駒がピン方向以外へ動いて取り返す非合法な利きを除外し、相手の利きが残っているマスへ玉が飛び込む手も禁止することで、王手やピンが絡む局面での誤判定を抑えています。
